## 7. Targeted timeout workaround and retry

Upstream CachyOS issue #236 and open PR #237 matched the missing explicit keyring timeout. The mirror-ranking command already had 3600 seconds; keyring setup inherited 30 seconds. The proposed change adds `timeout: 3600` only to the keyring command. The edit was tested locally against both source layout and repeated application; no full installer execution was tested on the older host.

User instructions were:

1. Reboot the USB session, keyboard lifted during startup, and reconnect Wi-Fi.
2. Launch the installer through Welcome once, allow preparation to finish, then close it at its first page. This avoids having the launcher overwrite the later configuration change.
3. Apply and inspect:

```bash
cfg=/etc/calamares/modules/shellprocess_initialize_pacman.conf
sudo sed -i.bak '/create-pacman-keyring/{n;s/verbose: true/timeout: 3600\n   verbose: true/;}' "$cfg"
grep -A2 create-pacman-keyring "$cfg"
```

Expected YAML block:

```yaml
 - command: "bash /etc/calamares/scripts/create-pacman-keyring"
   timeout: 3600
   verbose: true
```

Then launch directly:

```sh
pkexec-wrapper calamares -D6 2>&1 | tee -a ~/cachy-install.log
```

Repeat the same approved internal-disk layout, encryption, Limine and KDE choices. No whole-live-system upgrade, disabling of signature checking or mirror rewrite was required by this workaround. The 3600-second value is a maximum allowance, not an imposed one-hour delay. The standalone config edit disappears when that live environment is discarded; it is not a permanent installed-system patch.

The retry subsequently reached package installation and completed. The exact on-target edit output and the complete successful-install log were not supplied, so the outcome supports the workaround but is not a byte-for-byte verification of the edited file.

## 8. Slow download investigation

The user asked whether the keyboard could remain attached while the installer ran; guidance was yes, with it lifted again before restarting. The [15:22 photograph](../../evidence/2026-11-03-ux8407aa/20261103_152237.jpg) shows 17%, `Retrieving packages`, about **1308.65 MiB** total download, **3259.53 MiB** installed size for that batch, and regular/LTS kernels and headers in the package list.

The console's `Proceed with installation? [Y/n]` line had already been passed; it was not waiting for manual input. Repeated `Next slide` messages showed only slideshow activity, not network progress. Source inspection confirmed the pacstrap stage does not report a continuously increasing byte-based percentage.

System Monitor was suggested, but the user could not find it. Instead, in a **new Konsole tab**:

```sh
watch -n 2 cat /proc/net/dev
```

The first number after wlan0's colon is received bytes. The user first typed `157000000 1572500000`; the assistant caught the digit-count mismatch and asked whether the readings were **1,570,000,000** and **1,572,500,000**. The user confirmed. A 2,500,000-byte increase over two seconds is approximately **1.25 MB/s / 10 Mbps**. That implies roughly 18 minutes for the shown 1308.65 MiB batch at a sustained equivalent rate, not 18 minutes for the whole install. Interface counters include all traffic and are not an installer-specific measurement.

Progress then advanced 17% → 35% → 41% → 82% → complete. Advice was to keep power, USB and the original installer terminal connected/open until success. No cancellation/repartition cycle was triggered merely because a stage stayed at the same percentage.
